# 동네 광장 추천용 RAG 설계 해설

## 1. 한 문장 정의

동네 광장 추천용 RAG는 사용자의 관심사·편안한 참여 방식·가능 시간을 질의로 만들고,
현재 참여 가능한 활동 설명을 벡터로 검색한 뒤, 검색된 활동만 근거로 추천 이유를 생성하는
근거 기반 활동 추천 시스템이다.

RAG의 목적은 AI에게 아무 모임이나 지어내게 하는 것이 아니다. 동네 광장에 실제로 존재하고
지금 모집 중인 활동 가운데 사용자가 부담 없이 시작할 수 있는 연결을 찾는 것이 목적이다.

## 3. 왜 동네 광장에 RAG가 필요한가

일반 LLM은 우리 서비스의 현재 활동 목록을 학습하지 않았다. 오늘 생성된 독서 모임, 이미
정원이 찬 러닝 모임, 취소된 등산 모임을 알 수 없다. 활동 전체를 매번 아무 구분 없이
모델에게 주면 다음 문제도 생긴다.

- 존재하지 않는 활동을 지어낼 수 있다.
- 취소되거나 정원이 찬 활동을 추천할 수 있다.
- 활동 수가 늘수록 입력 토큰과 비용이 증가한다.
- 어떤 활동 정보 때문에 추천했는지 검증하기 어렵다.
- 사용자의 표현과 활동 글의 단어가 다르면 단순 키워드 검색이 놓친다.

예를 들어 사용자가 사람 많은 곳은 부담스럽고, 조용히 책을 읽고 싶어요라고 입력했을 때
활동 글에 혼자 읽다가 마지막에 짧게 감상을 나눠요라고 적혀 있으면 독서라는 단어가 직접
겹치지 않아도 의미는 가깝다. 임베딩은 이런 의미 유사도를 숫자 벡터의 거리로 비교한다.

## 4. 이 기능은 어떤 종류의 추천인가

현재 구현은 콘텐츠 기반 의미 검색 + 근거 생성이다.

- 콘텐츠 기반: 활동 제목·목적·설명·참여 방식으로 추천
- 의미 검색: 단어 일치가 아니라 임베딩 유사도로 후보 선택
- RAG: 검색된 활동 정보만 LLM에 넣어 추천 이유 생성
- 규칙 결합: 대화 부담, 초보 가능, 시간 조건을 메타데이터 보너스로 반영

현재 구현이 아닌 것:

- 다른 사용자 행동을 학습하는 협업 필터링
- 사용자의 성별이나 성비를 활용한 추천
- 심리 상태를 의료적으로 진단하는 모델
- 장기 참여 이력을 학습한 개인화 랭킹
- 인터넷 전체에서 활동을 검색하는 웹 RAG

MVP에서는 사용자가 직접 입력한 관심사와 편안함만 사용하는 것이 개인정보를 덜 쓰고
설명하기 쉽다.

## 5. 강의의 RAG 흐름과 프로젝트 대응

11차시 강의는 RAG를 수집과 질의로 나눈다.

    수집 흐름: 활동 데이터 → 정리 → 문서화 → 임베딩 → 벡터 인덱스

    질의 흐름: 사용자 조건 → 질의 임베딩 → top-k 검색 → 조건 보정
              → 추천 이유 생성 → 응답 검증 → 활동 카드

### 5.1 지식원

동네 광장의 RAG 지식원은 현재 모집 중이고 정원이 남은 활동이다.

포함하는 공개 필드:

- activityId
- 제목
- 활동 목적
- 설명
- 카테고리
- 대화 부담 정도
- 초보 참여 가능 여부
- 공개 장소
- 일정과 활동 시간
- 현재 인원과 최대 인원
- 모집 상태

포함하지 않는 필드:

- 실명
- 전화번호와 이메일
- 성별과 성비
- 비밀번호·인증 정보
- 비공개 참여자 정보
- API 키

추천 근거를 만드는 데 필요하지 않은 개인정보는 벡터 문서에도 넣지 않는다.

### 5.2 활동 하나가 하나의 의미 청크

11차시는 문자열 길이로 무작정 자르지 말고 의미 단위로 청킹하라고 설명한다. 동네 광장의
활동 글은 이미 제목·목적·설명·장소·일정이라는 하나의 완결된 의미 단위다.

따라서 MVP에서는 활동 하나를 하나의 청크로 본다.

예시 활동 문서:

    제목: 조용한 주말 독서
    목적: 각자 책을 읽고 마지막에 짧게 감상 나누기
    설명: 처음 오는 사람도 말하지 않고 참여할 수 있음
    카테고리: 독서·자기계발
    대화 부담: quiet
    초보 가능: true
    장소: 구립 도서관 열린 공간
    일정: 토요일 오후

활동 설명이 매우 길어지거나 공지·규칙·후기가 별도 문서로 늘어나면 목적, 참여 방식,
안전 규칙 등을 의미 단위로 나눠 여러 청크로 만드는 것이 적절하다. 현재 규모에서는
과도한 청킹이 오히려 같은 활동의 맥락을 분리한다.

### 5.3 문서 직렬화

api/_lib/automation.js의 activityText는 다음 공개 필드를 하나의 텍스트로 합친다.

    title | purpose | description | category | conversationLevel
    | beginnerFriendly | location | scheduledAt

구분자를 넣는 이유는 모델이 각 필드의 의미 경계를 유지하면서도 하나의 임베딩 입력으로
처리할 수 있게 하기 위해서다.

### 5.4 질의 만들기

recommendationQuery는 다음 정보를 합친다.

- 사용자가 적은 관심사
- 편안한 만남 방식
- 참여 가능한 시간
- 부담이 적고 공개 장소에서 함께하는 건강한 동네 활동이라는 서비스 목적

예시:

    관심사: 책 읽기
    편안함: quiet
    시간: this_week
    서비스 맥락: 부담이 적고 공개된 장소에서 함께하는 건강한 동네 활동

11차시는 검색용 질의에서 불필요한 명령을 빼라고 설명한다. 현재 UI 입력은 짧은 관심사
필드라 별도 LLM 질의 재작성까지 쓰지 않는다. 사용자가 긴 자연어를 입력하는 형태로
확장하면 추천해줘 같은 명령은 제거하고 핵심 관심사·제약만 검색 질의로 만드는 단계가
필요하다.

## 6. 임베딩과 벡터 검색

### 6.1 임베딩

임베딩은 텍스트의 의미를 숫자 배열로 바꾸는 과정이다. 비슷한 의미의 문장은 벡터 공간에서
비슷한 방향을 갖는다.

api/_lib/provider.js의 embedTexts는 서버에서 다음 작업을 한다.

- 서버 환경변수의 API 키 사용
- text-embedding-3-small 기본 모델 호출
- 질의와 활동 문서를 같은 모델로 임베딩
- 응답 개수와 벡터 형식 검증
- timeout과 제공자 오류 처리

질의와 문서를 같은 임베딩 모델로 만들어야 같은 벡터 공간에서 비교할 수 있다.

### 6.2 코사인 유사도

코사인 유사도는 두 벡터의 길이보다 방향이 얼마나 비슷한지를 본다.

    cosine(q, d) = (q · d) / (||q|| × ||d||)

- 1에 가까움: 의미 방향이 매우 비슷함
- 0에 가까움: 관련성이 낮음
- 음수: 의미 방향이 반대일 수 있음

api/_lib/automation.js의 cosineSimilarity가 점곱과 두 벡터의 크기를 계산한다.

### 6.3 top-k 검색

현재 처리:

1. 질의 벡터 1개 생성
2. 참여 가능한 활동 문서 벡터 생성
3. 각 활동과 코사인 유사도 계산
4. 점수가 높은 순으로 정렬
5. 상위 5개를 추천 생성 후보로 전달

top-k를 너무 작게 하면 좋은 활동을 놓치고 recall이 낮아진다. 너무 크게 하면 관련 없는
활동이 LLM 컨텍스트에 들어가 정밀도가 떨어지고 비용이 늘어난다. 현재 5는 활동 수가 적은
MVP의 시작값이며 골든셋으로 조정해야 한다.

## 7. 의미 점수와 서비스 조건의 결합

벡터 유사도만 사용하면 의미는 비슷하지만 사용자가 원하는 참여 방식과 맞지 않을 수 있다.
예를 들어 운동이라는 관심사는 맞아도 조용히 참여하고 싶은 사용자에게 대화가 활발한
대형 러닝 활동은 부담스러울 수 있다.

현재 rankRecommendationDocuments는 다음처럼 결합한다.

    fit = 정규화한 코사인 유사도 × 0.85 + 메타데이터 보너스

메타데이터 보너스:

- quiet 선호와 quiet 활동 일치
- light_conversation 선호와 같은 활동 일치
- active 선호와 active 활동 일치
- beginner 선호와 초보 가능 일치
- today 또는 this_week 시간 조건 일치

이 설계의 의미:

- 관심사 의미는 벡터 검색이 담당
- 참여 편안함과 시간 같은 명시적 조건은 코드가 담당
- LLM은 후보를 새로 만드는 것이 아니라 근거를 설명

정형 조건은 코드가 정확하고, 자연어 의미는 임베딩이 유연하다는 9차시의 도구 원칙을
추천에 적용한 것이다.

## 8. 검색 후 생성

api/automation.js의 runRecommendation은 top-5 후보만 recommendationPrompt에 전달한다.

추천 Agent의 제약:

- 검색된 후보 밖의 activityId 생성 금지
- 최대 3개만 추천
- 추천 이유는 후보 문서의 실제 정보에 근거
- fit은 0과 1 사이
- JSON 형식만 반환

모델 출력 후 sanitizeRecommendations가 다시 검증한다.

- 허용된 activityId 집합에 없는 추천 제거
- 이유가 빈 추천 제거
- fit을 0~1 범위로 제한
- 최대 3개
- 정책 버전 포함

이 단계가 RAG의 Generation이다. 검색 결과를 컨텍스트로 넣었더라도 응답 검증이 없으면
모델이 존재하지 않는 ID를 만들 수 있으므로 코드 게이트가 필요하다.

## 9. 실패와 fallback

| 실패 | 현재 처리 | 이유 |
|---|---|---|
| 모집 가능한 활동 없음 | 빈 추천과 조건 확장 안내 | 없는 활동을 생성하지 않음 |
| 임베딩 API 실패 | unavailable과 빈 추천 | 키워드 결과를 벡터 RAG로 가장하지 않음 |
| 추천 생성 LLM 실패 | 벡터 top-k 결과로 이유 생성 | 검색 근거는 이미 확보됨 |
| 모델이 없는 ID 생성 | 허용 ID 검증에서 제거 | 환각 차단 |
| 활동이 정원 초과·취소 | 문서 생성 전에 제외 | 참여할 수 없는 결과 방지 |
| 개인정보 입력 | 입력 계약에서 거절 | 벡터와 로그에 개인정보 저장 방지 |
| 프롬프트 주입 | 관심사 입력 거절 | 추천 Agent의 규칙 변경 방지 |

브라우저 main.js에는 정적 데모를 위한 로컬 추천 fallback도 있다. 이것은 키워드와 메타데이터
기반이며 실제 RAG가 아니다. 발표에서는 endpoint가 정상일 때 표시되는
embedding-cosine 또는 semantic-vector-cosine 근거와 로컬 fallback을 구분해야 한다.

## 10. 현재 구현은 진짜 벡터 RAG인가

예. 다음 세 요소가 실제로 존재한다.

1. Retrieval: OpenAI 임베딩 또는 고정 의미 축 벡터와 코사인 유사도로 활동 top-k 검색
2. Augmentation: 검색된 후보를 추천 프롬프트에 컨텍스트로 삽입
3. Generation: 후보만 근거로 추천 이유와 fit 생성

다만 현재는 프로덕션 벡터 DB RAG가 아니라 요청 범위 인메모리 벡터 RAG다.

현재 방식:

- 추천 요청마다 질의와 모든 활동을 함께 벡터화
- Embeddings 권한이 있으면 embedding-cosine을 우선 사용
- 현재 Vercel 키처럼 Embeddings가 403이면 Chat 모델의 16개 고정 의미 축 벡터를 사용하고
  embeddingFallback을 true로 기록
- 메모리에서 코사인 유사도 계산
- 서버 프로세스 밖에 벡터를 영속 저장하지 않음

강의의 프로덕션 방식:

- 활동 생성·수정 시 문서를 한 번 임베딩
- 벡터 DB에 activityId와 메타데이터를 함께 저장
- 추천 요청 시 질의만 임베딩
- 벡터 DB에서 top-k 검색과 상태 필터 수행

따라서 현재 구현은 RAG 원리와 사용자 흐름을 증명하는 MVP이고, 비용·지연·영속성은 다음
단계에서 개선해야 한다.

## 11. Supabase pgvector로 확장하는 구조

11차시는 이미 PostgreSQL을 사용한다면 pgvector로 추가 인프라 없이 벡터 검색을 도입할 수
있다고 설명한다. 동네 광장은 Supabase를 사용하므로 자연스러운 확장 경로다.

개념 데이터:

    activity_embeddings
    - activity_id
    - content
    - embedding vector(N)
    - category
    - conversation_level
    - beginner_friendly
    - scheduled_at
    - status
    - updated_at

수집 시점:

1. 활동 생성
2. 문맥 분류 Agent approved
3. 공개 필드로 활동 문서 생성
4. 임베딩 생성
5. activityId 기준 upsert

갱신 시점:

- 제목·목적·설명·카테고리 변경
- 일정 또는 참여 방식 변경
- 활동 취소·완료 시 검색 대상 제외

질의 시점:

1. 사용자 조건을 질의로 변환
2. 질의 임베딩 생성
3. recruiting, 정원 남음, 시간 조건 메타데이터 필터
4. pgvector 유사도 top-k
5. 필요 시 리랭킹
6. 추천 이유 생성

중요한 점은 벡터 DB로 바꿔도 브라우저의 요청·응답 계약은 바뀌지 않는다는 것이다.

## 12. 하이브리드 검색과 리랭킹은 언제 필요한가

11차시는 규모에서 벡터 검색만으로 부족할 수 있다고 설명한다. 하지만 강의의 Less is More
원칙에 따라 MVP에 모든 기술을 한꺼번에 넣지 않는다.

하이브리드 검색이 필요한 신호:

- 정확한 활동명이나 지역명이 벡터 검색에서 밀림
- 자격증명, 고유 프로그램명, 코드 같은 희귀 단어가 중요
- 오타·축약·고유명사 검색 요구가 많음

확장 방식:

- Dense: 임베딩 의미 검색
- Sparse: 키워드 또는 BM25 검색
- RRF: 두 순위를 결합
- Reranker: 넓게 찾은 후보를 질의와 함께 다시 정밀 평가

현재 활동 수가 적고 고유 식별자 검색이 핵심이 아니므로 벡터 검색 + 명시적 조건 보너스로
시작한다. 평가에서 검색 누락이 확인되면 하이브리드를 추가한다.

## 13. 캐싱

11차시는 응답 캐시, 검색 결과 캐시, 임베딩 캐시를 구분한다.

현재 프로젝트:

- main.js에 사용자 조건과 활동 업데이트 상태를 키로 쓰는 브라우저 결과 캐시 존재
- 서버 임베딩 캐시는 아직 없음

확장 우선순위:

1. 활동 content hash가 같으면 임베딩 재사용
2. 같은 질의와 같은 활동 인덱스 버전이면 검색 결과 재사용
3. 같은 사용자 조건과 같은 후보 집합이면 최종 응답 재사용
4. 활동 변경 시 관련 캐시 무효화

캐시 적중률만 높이고 오래된 활동을 추천하면 안 되므로 활동 updatedAt 또는 인덱스 버전을
키에 포함해야 한다.

## 14. 프로젝트 예시

### 예시 A: 조용한 독서

사용자 조건:

    interest: 조용히 책 읽기
    comfort: quiet
    timeWindow: this_week

검색:

- 조용한 주말 독서: 높은 의미 유사도 + quiet 보너스
- 영어 회화 모임: 일부 자기계발 의미만 일치
- 러닝 크루: 낮은 의미 유사도

생성 결과:

    조용한 주말 독서는 각자 책을 읽고 마지막에 짧게 감상을 나누는 방식이라
    대화 부담이 낮고 이번 주 참여 조건에 맞아요.

### 예시 B: 처음 시작하는 운동

사용자 조건:

    interest: 몸을 움직이고 싶지만 운동 모임은 처음
    comfort: beginner
    timeWindow: any

검색과 보정:

- 초보 산책: 의미 유사도 + beginner 보너스
- 고강도 러닝: 의미는 일부 일치하지만 beginner 불일치
- 보드게임: 활동 의미 불일치

RAG는 산책을 후보로 찾고, 코드 조건은 초보 가능 활동을 위로 보정한다.

## 15. 평가 설계

11차시 강의처럼 검색 품질과 생성 품질을 분리해야 어디를 고칠지 알 수 있다.

### 15.1 검색 골든셋 구조

각 케이스:

    {
      "query": {
        "interest": "조용히 책 읽기",
        "comfort": "quiet",
        "timeWindow": "this_week"
      },
      "expectedActivityIds": ["book-quiet"],
      "forbiddenActivityIds": ["cancelled-book", "full-book"],
      "reasonEvidence": ["quiet", "beginnerFriendly"]
    }

추천 골든셋 범주:

- 동의어: 독서 ↔ 책 읽기
- 완곡 표현: 말 많이 안 해도 되는 활동
- 복합 조건: 운동 + 초보 + 이번 주
- 정확 조건: 특정 카테고리·시간
- 정원·상태 제외: full, cancelled
- 결과 없음
- 개인정보·주입 거절
- 활동 데이터 변경 후 인덱스 갱신

### 15.2 검색 지표

| 지표 | 질문 | 프로젝트 사용 |
|---|---|---|
| recall@5 | 기대 활동이 top-5 안에 있는가 | 좋은 후보를 놓치지 않는지 |
| precision@5 | top-5 중 관련 활동 비율은 얼마인가 | 노이즈가 많은지 |
| MRR | 첫 기대 활동이 몇 등인가 | 첫 추천 품질 |
| nDCG | 더 적합한 활동이 위에 있는가 | 복수 관련 활동의 순위 품질 |

검색 recall이 낮으면 프롬프트를 고쳐도 정답 활동이 모델에게 전달되지 않는다. 먼저 문서화,
질의, 임베딩, top-k를 점검해야 한다.

### 15.3 생성 지표

| 지표 | 의미 |
|---|---|
| grounded ID rate | 추천 ID가 검색 후보 안에 있는 비율 |
| Faithfulness | 추천 이유가 활동 문서에 실제로 근거하는가 |
| Relevance | 이유가 사용자의 관심사·편안함 질문에 답하는가 |
| private data leakage | 이유에 비공개 정보가 포함되지 않았는가 |
| empty-state correctness | 적합한 후보가 없을 때 지어내지 않는가 |

필요하면 11차시의 LLM-as-a-Judge처럼 질문, 검색 후보, 추천 이유, 평가 Rubric을 별도 Judge에
주어 Faithfulness와 Relevance를 채점할 수 있다. Judge는 temperature 0과 고정 Rubric을
사용하고 가능하면 생성 모델과 다른 모델로 교차 평가한다.

### 15.4 현재 검증된 범위

- tests/code-automation.mjs에서 벡터 방향에 따라 관련 활동이 먼저 정렬되는지 검증
- 허용되지 않은 개인정보 입력 거절
- 정원이 찬 활동 제외
- tests/evaluate.mjs에서 기본 추천 fixture 3개 통과
- provider mock 검증에서 embeddings와 chat completions 두 경로 호출 확인

현재 부족한 증거:

- 실제 강사 API 키로 만든 임베딩의 recall@k
- 20개 이상 추천 골든셋
- 생성 이유의 Faithfulness Judge 점수
- 실제 활동 데이터가 늘어났을 때 지연·비용
- 사용자 첫 참여 완료율과 다시 참여 의향의 온라인 지표

## 16. 제품 성공 지표와 RAG 지표의 차이

RAG 검색 점수가 높다고 서비스 목적이 달성된 것은 아니다.

기술 지표:

- recall@5
- MRR
- Faithfulness
- 응답 지연
- 캐시 적중률

제품 지표:

- 추천 카드에서 활동 상세 보기 비율
- 추천 후 실제 참여 전환율
- 첫 참여 완료율
- 활동 후 다시 참여하고 싶은가 응답
- 추천 활동의 취소·이탈률

동네 광장의 MVP 가설은 좋은 검색 자체가 아니라 부담이 적은 활동을 통해 사회적 재연결이
일어나는가다. 따라서 기술 지표와 참여 결과를 함께 봐야 한다.

## 17. n8n과 순수 코드의 관계

| 논리 단계 | n8n 표현 | 순수 코드 |
|---|---|---|
| 트리거 | Webhook 입력 | POST /api/automation |
| 입력 검증 | 검증 및 정규화 | validateEnvelope |
| 지식원 선택 | activities 입력과 모집 상태 | buildRecommendationDocuments |
| 임베딩 | 보호된 provider 호출 | embedTexts |
| 검색 | 의미 검색 단계 | cosineSimilarity + rankRecommendationDocuments |
| 생성 | 추천 분류/생성 모델 | recommendationPrompt + chatJson |
| 후처리 | 보류·게시 분기 | sanitizeRecommendations |
| 응답 | Respond to Webhook | jsonResponse |

기존 n8n workflow는 전체 활동을 LLM에 전달하는 구조였고, 현재 순수 코드 경로는 실제
임베딩 top-k 단계를 명시적으로 갖는다. 따라서 벡터 RAG를 시연할 때는 코드 경로가 더
정확한 구현 증거다. n8n은 트리거→검증→AI→분기→응답이라는 오케스트레이션 구조를 보여주는
보조 자료로 남길 수 있다.

## 19. 발표에서 설명할 문장

추천 발표 문장:

“일반 LLM은 저희 서비스에 지금 어떤 활동이 모집 중인지 알지 못합니다. 그래서 사용자의
관심사와 편안한 참여 방식을 질의 벡터로 만들고, 실제 모집 중이며 정원이 남은 활동 문서를
같은 임베딩 공간에서 코사인 유사도로 검색합니다. 상위 5개 활동만 추천 Agent에 전달하고,
Agent가 검색 후보 밖의 활동을 만들면 코드에서 제거합니다. 즉 AI가 활동을 지어내는 것이
아니라 실제 활동을 검색한 뒤 그 근거를 설명합니다.”

시연 순서:

1. 활동 찾기에서 조용히 책 읽기와 quiet 선택
2. 추천 요청 중 추천 RAG 상태 표시
3. 독서 활동 카드와 벡터 검색 근거 표시
4. 추천 이유가 실제 활동 설명과 일치함을 확인
5. 정원 찬 활동이 후보에서 제외됨을 설명
6. 벡터 테스트와 향후 pgvector 구조 제시

## 20. 현재 한계와 다음 개선 순서

현재 완성된 부분:

- 실제 OpenAI 임베딩 경계
- 코사인 유사도 top-k
- 공개 활동만 지식원으로 사용
- 편안함·시간 메타데이터 결합
- 검색 후보 기반 추천 생성
- 허용 ID 검증과 벡터 fallback
- 개인정보와 API 키 분리

다음 개선 순서:

1. 강사 API 키를 Vercel 서버 환경변수에 등록해 실제 임베딩 실행
2. 20개 이상 추천 골든셋과 recall@5·MRR 측정
3. 활동 임베딩을 Supabase pgvector에 영속 저장
4. 활동 수정·취소 시 증분 인덱스 갱신
5. 임베딩·검색 결과 캐시
6. 검색 누락이 관찰될 때만 하이브리드 검색과 리랭킹
7. 참여 전환·완료·재참여 의향 온라인 지표 연결

MVP 발표에서는 현재 인메모리 RAG를 프로덕션 벡터 DB라고 과장하지 않는다. 대신 검색,
증강, 생성이 실제로 동작하고 인터페이스를 유지한 채 pgvector로 확장 가능한 구조라는 점을
명확히 설명한다.
