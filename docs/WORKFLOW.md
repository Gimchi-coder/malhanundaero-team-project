# 개발 워크플로우

## 상태 보드

| 상태 | 의미 | 이동 조건 |
|---|---|---|
| TODO | 아직 시작하지 않음 | 담당자와 범위가 정해짐 |
| IN PROGRESS | 현재 작업 중인 유일한 태스크 | 작업 시작 보고 후 |
| HUMAN REVIEW | 구현·검증 완료, 사람 검토 대기 | diff와 검증 결과가 있음 |
| MERGING | 승인된 변경을 병합하는 중 | 명시적 승인 후 |
| DONE | 사람 검토·병합 완료 | 최종 확인 후 |

한 번에 하나의 태스크만 `IN PROGRESS`로 둔다.

## 표준 순서

1. `git status`와 현재 변경사항 확인
2. 관련 PRD/SPEC/PLAN/TASKS/AGENTS 읽기
3. 목표·범위·수정 파일·검증 계획 제시
4. 사용자 승인
5. 테스트 또는 검증 조건 작성
6. 작은 단위로 구현
7. 문법 검사·관련 테스트·`git diff --check` 실행
8. `HUMAN REVIEW` 보고
9. 사용자가 diff 승인 후 다음 태스크 또는 병합 진행

## 문서 흐름

`team_prd.md → specs/.../spec.md → plan.md → data-model/contracts → tasks.md → code → tests`

문서마다 같은 내용을 복사하지 않는다. 상세 요구사항은 SPEC, 설계는 PLAN, 실행 순서는
TASKS에 둔다.

## 변경 단위 규칙

- 한 변경은 한 사용자 가치 또는 한 검증 가능한 개선을 다룬다.
- 전역 설정·공통 adapter·보안 정책 변경은 영향 범위를 먼저 설명한다.
- 기존 변경사항과 겹치면 덮어쓰지 않고 사용자에게 충돌을 알린다.
- 파일 삭제·대규모 재구성은 대상·이유·복구 방법을 먼저 제시한다.

## 완료 기준

- 요구사항과 acceptance scenario가 구현됨
- 정상·경계·오류·보안·개인정보 경로가 검증됨
- 사용자에게 이해 가능한 실패·복구 상태가 있음
- diff가 작고 설명 가능함
- 사람의 Git diff 검토가 끝남
